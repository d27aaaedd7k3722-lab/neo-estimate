## 0. なぜ本体を読むのか

このアプリは見積書 PDF から **コグニ互換の `.neo`** を作る。
互換性の答え合わせは今まで 2 つの方法でやってきた。

1. 実機が残した `.neo` を読む（347 本）
2. コグニを手で動かして保存した `.neo` と比べる

3 つ目として **実行ファイルとデータファイルを直接読む**道が使える。
2026-09-21 に初めて中を見たところ、その日のうちに使える事実が 4 つ取れた（§1）。

**重要な教訓**: 「実機データに例が無い」は「正解が分からない」ではない。
費用行の消費税は 347 本に 1 件も例が無かったが、コグニを 5 分操作したら確定した（§1-3）。

### 1-3. 費用行の消費税は請求書単位と同じ端数処理（実機で確定）

| 四捨五入 | 1 | 11 | 116 | 11 |

### 1-4. コグニの保存 = `.neo` そのもの

「名前を付けて保存」のファイルの種類が **「コグニセブン見積ファイル」= `.neo`**。
保存名の先頭に `MMDDHHMM` が自動で付き、既定の保存先は Z ドライブの案件フォルダ。
（テストで作った `.neo` は実案件フォルダに残るので、必ず消すこと）

### 1-5. 塗装材料費の単価表（48 行）→ 材料代の検算に使った（2026-09-21 夜に実装）

`AudaData\AnUsrTblPnt.sld`（SQLite）の `MaterialRate` テーブル。列は `LineNo, Paint, Coat, HFPainting, MaterialRate`。

**訂正**: 以前ここに「印字の材料代が『塗装指数 × この単価』と桁違いなら…」と書いたが、**式が違っていた**。
値は円ではなく **割合（％）の 100 倍**（2300 ＝ 23%）で、コグニの材料代は

```
塗装材料代 ＝ 塗装工賃計 × 材料代割合（整数 %。端数処理は工場ごと。既定は 10 円四捨五入）
```

（vendor の `reference/painting.md` §7 と `estimate_to_neo.cogni_default_material_rate` が同じ表を `/100` で読んでいる。
表は「工場が何も変えないときの既定」で 12〜25%、実案件は工場の設定で 21〜31% が多い）

| Paint | Coat=0 | Coat=1 | Coat=2 | Coat=3 |
|---|---|---|---|---|
| **0** HF=0 | 12% | 13% | 14% | 13% |
| **0** HF=1 | 23% | 22% | 23% | 22% |
| **0** HF=2 | 16% | 16% | 17% | 17% |
| **2** HF=0 | 12% | 14% | 15% | 15% |
| **2** HF=1 | 23% | 24% | 25% | 24% |
| **2** HF=2 | 16% | 17% | 18% | 18% |
| **3** すべて | 0 | 0 | 0 | 0 |
| いずれも HF=3 | 0 | 0 | 0 | 0 |

- `Paint` は `PaintingPlan.Paint − 1`（0 速乾 / 2 ２Ｋ / 3 水性）、`Coat` は `PaintingPlan.Coat − 1`、`HFPainting` は高機能塗装
- 表の値そのものは既定値なので、**検算の物差しには実案件の分布を使った**。実案件 NEO 2,500 本（Z:\ドキュメント、
  指数入力で材料代のある 1,564 本）の「材料代 ÷ 塗装工賃計」は 最小 3.0% ／ 1% 点 19.0% ／ 中央 26% ／ 99% 点 47.8% ／
  最大 74.1%。**5〜60% に 99.8% が入る**（外れは 3 本）
- 実装: `neo_skill/reader.py` の `_paint_material_note`。読み取りの最後の header の `paint.total`（塗装工賃計）と
  `paint.material`（材料代）で比を取り、5〜60% を外れたら「桁の読み違いの疑い」を画面の「読み取りの注意」と
  報告文（アプリ側で判断した点）に出す。**金額は動かさない・合否も変えない**。0 の数の読み違い（1/10・10 倍）は必ず外れる

### 2-2. 塗装の計算構造の地図（`Bin\AnPntBL*.bpl`）★ 未解明の外れに直結

BPL は C++Builder のパッケージで、**クラス名とメソッド名がそのまま読める**（マングル名）。

#### パネル塗装 `AnPntBLPnl.bpl`（115,200 バイト）

参照する表のクラス:
`TRC_XXX20List` / `XXX25` / `XXX77` / `XXX87` / `XXX97` / `XXX99`
`TRC_BoothList`（ブース）/ `TRC_ScrachList`（スクラッチ）/ `TRC_SiruList` / `TRC_PmashiList`
`TRC_T_Kei1List`〜`TRC_T_Kei4List` / `TRC_F_SList` / `TRC_H_N_SszList` / `TRC_Hju_SsList`
`TRC_PaintingPanelList` / `TRC_PaintingLinkPartsList`

メソッド:
`CalculateAllPanel` / `CalculateTime` / `CalculateAddTime` / **`CalculateAddBaseTime`（加算基礎）** /
**`CalculateBoothAddTime`（ブース加算）** / `CalculateSum` / `GetTimeTotal` / `GetWageTotal` /
`GetMaterialTotal` / **`GetMaterialByManualOfRateType`**（材料率の種類ごと）

#### 内板骨格 `AnPntBLFrm.bpl`（118,272 バイト）

表: `TRC_NaikokuAList` / `TRC_WNaikokuAList`（W = 水性）
部位は **5 つだけ**: `ERoom`（エンジンルーム）/ `FPillar` / `CPillar` / `RFPan`（ルーフパン）/ `FFApron`
各部位に `Time` / `Wage` / `Material` と、その `ByManual`（手入力）版がある。

#### バンパ `AnPntBLBmp.bpl`（135,168 バイト）

**`CalculateTime0` と `CalculateTime1` の 2 系統**がある。
→ 2026-09-21 に実案件から見つけた「FBANPA.DB の 6 値は 3 列 × 2 群
（塗装パネルがある見積 / バンパだけ塗る見積）」と符合する。**本体側から裏が取れた**。

入力: `Get_FRBumperForm`（形状）/ `Draft`（下地）/ `Color` / `Get_BumperCoat` / `CoatFlag` / `Version`、
FR と RR で対になっている。列挙型 `TCTBumperType`（`Udc_constant` にある）。

#### その他 `AnPntBLOtr.bpl`（48,128 バイト）

表は `TRC_PaintingOtherList` のみ。メソッドは `CalculateSum` / `GetWageTotal` だけで
**指数計算を持たない**（＝追加項目は工賃をそのまま足すだけ）。

**なぜ未実装か**: メソッド名は読めても**係数と条件分岐は逆アセンブルしないと出ない**。
いまは「何を入力に取るか」が分かった段階。

**どう使えるか**: 実機実験の当たりが劇的に付く。
たとえば「ブース加算が独立メソッドで存在する」と分かれば、
ブース有り／無しの 2 本をコグニで作って差を取れば係数が出る。

### 2-3. ADDATA の表の分布 ★ いちばん有望な手がかり

1,307 車種フォルダを数えた結果（フォルダ名 + 2 桁 + `.DB`）:

| 番号 | 割合 | 番号 | 割合 | 番号 | 割合 |
|---|---|---|---|---|---|
| 01 / 11 | 100% | 06 | 93% | 89 | 74% |
| 79 | 99% | **20** | **92%** | 23 | 55% |
| 05/07/08/09/10 | 99% | **25** | **92%** | 93 | 54% |
| 15 | 94% | 12/17/26 | 91% | 13 | 52% |
| | | 76 | 87% | **77** | **33%** |
| | | 66 / 96 | 78% | **97** | **27%** |

**いまアプリが塗装パネルで見ているのは 77 / 97 / 87 / 99 だけ。
ところが 77 は 33%・97 は 27% の車種にしか無い。**
一方 BPL が列挙している **20 / 25 は 92% の車種にある**。

覗いた限り `C1020.DB`（1,180 バイト）は LF/RF/ASSY と部品番号の対応表に見えたので、
20/25 が塗装パネルの数値表そのものとは限らない。ただし
**「残り 3 分の 2 の車種で何を見ているか」は未解明**で、
ここが **標準指数の外れ 4%・塗装パネルの外れ 0.8%** に直結している可能性が高い。

## 3. 解析で「効かない」こと（期待しないこと）

- **AI の読み取り精度** — コグニとは無関係。見積書 PDF をどう読むかの問題
- **ADDATA の数値そのもの** — すでに読めている（標準品番・標準指数・塗装パネル表）
- **合計の一致** — すでに受け入れテスト 20 案件で不一致 0

## 4. 次にやるなら（推奨の順番）

1. **BPL の全クラス・メソッドを機械的に地図にする**（`AnPntBL.bpl` / `AnPntBLOpt.bpl` / `AnPntUI.bpl` も）
   → どの表をどの順で引くかの骨格が見える
2. **アプリが使っていない表を特定する**（20/25 のほか `T_Kei1〜4` / `F_S` / `H_N_Ssz` / `Hju_Ss` / `Siru` / `Pmashi`）
   → 実データの構造を読み、塗装・指数のどれに効くか判定
3. **コグニ実機で該当ケースを作って答え合わせ**
   → 消費税のときと同じやり方（条件を 1 つだけ変えて 2 本保存し、差を取る）

### 実機実験の型（消費税で使って成功した手順）

1. 新規見積 → 基本単価 → メーカーから検索 → 車名 → モデル → 年式 → ボディ形状 → エンジン型式 → グレード
   → 装備バリエーションは**何も選ばず完了**（トヨタ アイシス 5ドアワゴンが最短）
2. 調べたい値を入れる（セルは**ダブルクリックしてから**打つ。1 回クリックでは編集モードにならない）
3. 条件を 1 つだけ変えて 2 本保存する
4. `.neo` を読んで差分を取る
5. **テストファイルは実案件フォルダに残るので必ず消す**（控えを取ってから）。設定も元に戻す
