## 1. このアプリは何か

車両修理の見積書（PDF／CSV）を読み取り、コグニセブン（AdSeven）の
`.neo` ファイルに変換する Streamlit アプリ。

- 本番: https://shouchiku-neo-estimate.streamlit.app/
- リポジトリ: `d27aaaedd7k3722-lab/shouchiku8-app`
- デプロイ: Streamlit Community Cloud が `main` から自動デプロイ

### 絶対条件

生成された `.neo` は **協定見積として保険会社に提出される**。したがって

> **元の見積書と、同じ明細行・同じ金額・同じ部品・同じ車であること**

これが他のすべてに優先する。行が1本増えても減っても、1円違っても使えない。
「合計だけ合っていればよい」ではない。この判断基準は、以下のすべての設計判断の
根拠になっている。

## 3. 過去に本番が停止した原因（同じ轍を踏まないために）

「なんてこった。／Oh no. Error running app.」で本番が起動しなくなった事故が
2回あり、原因は両方ともデプロイ設定だった。

### (1) `requirements.txt` の Python 版の下限

`streamlit==1.63.0` は Python 3.10 以上、`pandas==3.0.5` は 3.11 以上が必須。
Cloud 側の Python が 3.9/3.10 だとビルドが失敗して起動しない。

→ **環境マーカーで 3.9〜3.14 のどれでも入る組み合わせを指定してある。**
バージョンを上げるときは、下限の Python でも入るかを必ず確認すること。

### (2) `.streamlit/config.toml` に Cloud Run 向けの設定を書いた

以下は **Community Cloud では書いてはいけない**：

| 設定 | 理由 |
|---|---|
| `server.port` / `server.address` / `browser.serverAddress` | ポートはプラットフォームが割り当てるため固定不可 |
| `server.enableCORS = false` / `server.enableXsrfProtection = false` | Cloud は自前のプロキシ越しに配信しており、既定値を前提にしている |
| `server.enableWebsocketCompression = false` / `runner.fastReruns = true` | Cloud Run の WebSocket 切断への回避策で、ここでは不要 |

Cloud Run / Docker では `start.py` が `--server.address` と `--server.port` を
コマンドライン引数で渡しており、そちらが `config.toml` より優先される。
**つまり config.toml を Community Cloud 向けに保ったままで Cloud Run も動く。**
config.toml 冒頭に同じ注意書きを残してある。

## 5. 直した内容（分類別）

### 5.1 元見積に無い行を作る／総額を変えていた

PDF経路の合計突き合わせが最大の問題領域だった。

| 症状 | 実測 |
|---|---|
| 合計欄が税抜の見積で、マイナスの調整行が1本増え総額が9.09%減る | 3行/¥385,000 → 4行/¥350,000 |
| 値引き行を「読み落とし」と誤解し、打ち消す行を作る | 値引きが実質無効化 |
| 上2つが重なる | 原本 ¥594,000 → ¥660,000（+¥66,000） |
| 小計に含まれない行（レッカー代等）で2つの補正が打ち消し合う | 部品計 ¥500,000 → ¥520,000 |
| 印字小計が値引き後の帳票で、値引きを二重に引く | 4行/¥605,000 → 5行/¥550,000 |

原因は「印字された総合計が税込か税抜かを表記の選択だけで決め打っていた」ことと
「印字された部品計・工賃計が値引き前とは限らない」ことを考慮していなかったこと。

**方針の変更**: どちらの税区分の解釈でも説明できない大きな差は、
**行を捏造せず警告だけ**にした。合計だけ合わせるために原本に無い行を入れるより、
差があることを知らせるほうが安全という判断。読み落としを模した入力では
従来どおり調整行が入り警告も出ることを確認済み（安全網は無効化していない）。

### 5.2 無言で総額が不足する／行が消える

**読み落とし額が消費税に化ける** — 税込表記で明細を1行落とすと、
その不足額がちょうど消費税額に見えて「総合計は税込・明細は正しい」と
誤判定され、3つの安全網が同時に外れていた。

```
原本 3行 / ¥1,100,000  →  生成 2行 / ¥1,000,000（-¥100,000）
警告 0件・画面には「✅ 解析完了」「🔍 検証OK」
```

無警告帯は総合計の 7.09〜11.09%（総額500万円なら ¥354,500〜¥554,500 が素通り）。
税区分を**明細合算とは独立した証拠**（印字された部品計＋工賃計−値引）から
決めるよう改めた。読み落としはこの値に影響しないので化けない。

**少額の行が無警告で消える** — 残差警告の下限が総額の0.1%だったため、
60万円の見積で600円のクリップ1行が調整行も作られないまま消えていた。

### 5.3 同じ入力から違う `.neo` が出る

```
1回目: 3行 / 部品 ¥100,000 / 工賃 ¥50,000
2回目: 2行 / 部品 ¥90,000  / 工賃 ¥60,000   ← 同じPDF・同じ操作
```

生成側が解析結果の dict に「調整後の合算」を書き戻しており、
その dict は解析キャッシュそのもので**プロセス全体で共有**（セッション跨ぎ・
利用者跨ぎ）だった。1回目の出力が2回目の入力になっていた。
キャッシュの出し入れ両方で `copy.deepcopy` するようにした。

> **Streamlit Community Cloud は1プロセスを全利用者で共有する。**
> モジュールレベルのキャッシュ・グローバル変数は他人にも見える。
> 参照を返すキャッシュは、呼び出し側が書き換えると汚染される。

### 5.4 画面の表示と生成物が食い違う

利用者は生成前に画面で原本と突き合わせる。アプリ自身も警告文でそれを促している。
**プレビューが `.neo` と違えば、その確認は無意味になる。**

- CSV取り込みで、何も突き合わせていないのに「PDF原本とNEO転記内容が
  完全一致しています」と断言していた（比較相手が「PDF記載 ¥0」のまま ✅）
- 「※金額調整」の警告が「+0円のずれ」と表示しながら ±10,000円の行が1本入る
- 税込表記で画面の合計と `.neo` が1円ずれるのに「完全一致」と表示
- プレビューの数量が、部品金額0の行では `.neo` に入らない
- CSVで品名が空欄の行を、金額があっても黙って落としていた

### 5.5 コグニセブンに渡る値の誤り

**作業区分コードが1つずれていた** — `ERParts.DisposalCode` を
取替=1/脱着=2/修理=3/鈑金=4 で書いていたが、実機NEO 244件の解析で確定している
対応は **取替=0/脱着=1/修理=2**（鈑金・塗装を含む）。リポジトリ内の読み取り側
2か所は最初から 0/1/2 を使っており、書き込み側だけが根拠なく1始まりだった。
画面の文字（取替/脱着）は正しく出るので**目視では気づけない**。

**指数（工数）がNEOに1つも入っていなかった** — 取り込み・表示・編集まで
させておきながら書き出し直前に捨てていた。全角「１．５」や「2.0時間」も
金額と同じ正規化で読めるようにした。

**Addata照合が別の部品を当てていた**
- 左右が食い違う部品に当たる（照合器が左右を落とすだけで使っていなかった）
- ホンダの15バイト品番だと価格相違の「※価」が黙って消える
- ADDATAの指数が見積の工数を書き換える（工賃は見積の値のまま）
- 未マッチ行の「※」で末尾の左右が消え、左右の部品が同じ文字列になる
- 車種が2候補に割れても「連携成功」としか出ない

### 5.6 消費税の丸め

**請求書単位で1回だけ丸める。** これが見積書に印字された税込総額の作り方であり、
インボイス制度の原則でもある。一度バケットごとの丸めに変えたところ、
`.neo` の総額が原本から1円ずれるケースが 25.5%（税抜）／26.9%（税込）発生した。

内訳の税額欄（部品計・工賃計・諸経費計）との差は、
**いちばん金額の大きい欄に寄せて** `tx_Total` との整合を保っている。

**税込表記の行ごとの丸め差は、1行に寄せず全行に1円ずつ配る。**
1行に寄せると明細が増えるほどその行だけ原本から離れる
（1,000行の見積で1行が455円ずれていた）。

### 5.7 過去の `.neo` をテンプレートに使ったときの残留

以下が前案件のまま残っていた：見積ID・案件番号・**協定額**（`Statistics`）／
金額付きの調整行（`Fixer`）／予備明細（`ReserveERParts`、しかも参照先の
`RecordNo` は新しい明細に存在しない）／塗装作業名・費目名・フレーム修正の
入力条件／ヘッダXMLの立会者名（個人情報）・伝票番号・備考・グレード。

見積ID・案件番号・協定額は**マージモードでも必ず消す**。
アプリにこれらの入力欄が無く、残ると利用者は消せないため。

また、出荷テンプレートの費目名「ｺｰﾃｨﾝｸﾞ修正部再施工」が、
このアプリで作った `.neo` **すべて**に入っていた（`Expense` のクリアが
金額とコメントだけで `Name` を消していなかった）。
固定費目名（`NameFix=1` の LineNo 1〜8）は残す。

### 5.9　本番で作った .neo の日付が1日前になっていた（2026-09-10）

`datetime.datetime.now()` をタイムゾーン無しで使っていた。本番の
Streamlit Community Cloud のコンテナは日本時間ではないため、
JST 2026-09-10 09:13 の時点で画面に「見積日: 2026/09/09」と出ていた。

NEO に実際に書かれるのは次の2箇所で、どちらも1日前の日付になる。

| 書き込み先 | 中身 |
|---|---|
| ヘッダXML `CreatedDate` | 見積の作成日 |
| `AnSvEm0001Ex.db` | `estimated_date`（見積日） |

JST 固定の `now_jst()` を定義し、`app.py` の `datetime.datetime.now()`
7箇所すべてを置き換えた。夏時間の無い固定オフセット
（`datetime.timezone(datetime.timedelta(hours=9))`）なので `tzdata` に依存しない。

### 5.10　コグニセブンの一覧に「どの車の誰の見積か」が出ていなかった（2026-09-10）

「どの車の誰の見積か分からない」状態で並ぶ。協定見積として渡す書類なので実害が大きい。

切り分けたこと（実機で1つずつ試した）:

| 試したこと | 結果 |
|---|---|
| 内包の `<保存名>.xml` の名前をファイル名に合わせる | 直らない |

→ 一覧は内包ファイルを一切見ておらず、**ファイル先頭 424 バイトの管理領域**だけを読んでいた。
アプリは出荷テンプレート（顧客情報が空）の管理領域を丸写ししていた。

`neo_header.py` を新設して、ここに 顧客名・車名・登録番号・作成日・金額 を書くようにした。
管理領域は XOR 0xFF ＋ ビットシフトの2ブロック構成で、
**実機 202 件で「復号 → 同じ値で再生成 → 元と1バイトも違わない」ことを確認**している。

移植のときに1点直した: Windows の IBM 拡張漢字（`cp932w`）の置き換え対象を
「cp932 が ED/EE 行に落とす字（德・髙・﨑）」だけに絞った。
元の実装は「㈱」も IBM 行（`FA 58`）にしていたが、実機は cp932 の `87 8A` で書いていた。

修正後、実機のコグニセブンで「品川300あ1234 / テスト太郎 / ﾉｱ」と
正しく一覧に出ることを目で確認した。

#### 管理領域の中身

先頭 424B。`raw[0:9]` が `'NEO300101'`、残りは XOR 0xFF ＋ ビットシフトの2ブロック。

| ブロック | 復号 | 位置 | 内容 |
|---|---|---|---|
| A | `((raw[9:424] ^ FF) as big-int) << 3` | `A[74:114]` | 協定工場名（40B） |
| | | `A[114:144]` | 顧客名（30B） |
| | | `A[144:206]` | 車名（62B。`Car.CarNameByUser` と同じ値） |
| | | `A[206:210]` | 作成日（u16 年, u8 月, u8 日） |
| | | `A[210:250]` | double×5 = 部品計 / 工賃計 / 塗装計 / **諸経費計** / 総額(税込) |
| | | `A[274:302]` | 陸運支局(8B) 分類番号(6B) かな(4B) 一連番号(10B) |
| B | `((raw[330:424] ^ FF) as big-int) << 7` | `B[0:7]` | 保存日時（年月日 時分秒） |
| | | `B[7:15]` | ライセンスID（8B） |

**諸経費計には非課税ぶんも入る。** 非課税は課税額計（`SubTotal`）には入らないのに、
この欄には入っている。非課税のある実機 12 件すべてで
「ヘッダの値 = 課税諸経費 + 非課税」だった。

管理領域は**生成し終わった見積本体**（`AnSvEm0001Ex.db` の Customer / Car / Insurance と
`AnSMB.txt` の Total）から作っている。テンプレート側の管理領域は見ない。
そうしないと、本体には顧客が入っているのに管理領域だけ空、という
古いアプリ製の `.neo` をテンプレートに使ったときに一覧が空欄のまま残る。

### 5.11　実機と食い違っていた値（2026-09-10）

### 5.12　配布パッケージの仕様書と突き合わせて直したもの（2026-09-11）

`pdf-to-neo_bundle_20260910.zip`（スキル `pdf-to-neo` と生成器 `claude_neo_pipeline` 一式、
NEO 仕様書 108KB・ADDATA 逆引き仕様 78KB・判断規則 41KB）を改めて精査した。
差分の候補は多数出たが、**実機の `.neo` 202件・実機が印刷した見積書PDF・実機の定義ファイルで
裏が取れたものだけ**を採用した。

#### 採用したもの

- **NEO に書く文字が Windows と違う符号だった。**
  Python の `cp932` は「﨑」「德」「髙」を NEC 選定の ED/EE 行に書くが、
  Windows（コグニセブン）は IBM 拡張の FA〜FC 行に書く。
  実機202件のテキスト部を CP932 の文字境界を追って走査したところ、
  **ED/EE 行は 0 箇所、FA〜FC 行が 7 箇所**（「濱﨑」「竹﨑」の﨑 = `fa b1`）だった。
  ヘッダXML・`AnSvImge.ini`・`AnNote.ini` と幅の切り詰めを `cp932w` に統一。
  見積本体DB（SQLite）は実機も UTF-8 なので変えていない（実機ファイルで確認）。
  なお「㈱」は cp932 の `87 8a` のまま（実機がそう書いていた）。IBM 行に移すのは
  「cp932 が ED/EE 行に落とす字」だけ。

- **指数の括弧書きを負数と取り違えていた。**
  金額の `(5,000)` は会計表記のマイナス（値引き）だが、**指数の括弧はただの印字**。
  コグニセブンが印刷する見積書は
  「加算基礎数値 ( 1.50) 11,000」「ブース加算 ( 0.50) 3,670」と括弧付きで指数を出す
  （実機の帳票PDFで確認）。金額と同じ数値変換を通していたため、
  **コグニ印刷の見積書を読み込むと指数のある行が全部「指数なし」で出ていた**。

- **前案件の塗装オプションが残っていた。**
  `PaintingEtcetera` の `BSealing`（ボデーシーリング）・`ARWax`（防錆ワックス）・
  `TwoCSolidOther`（2コートソリッドのルーフ以外の枚数）を消していなかった。
  金額だけ 0 にしてフラグを残すと、コグニで開いて再計算したときに
  前案件ぶんの塗装工賃が乗る（実機の例で 730+730+2,200 = 3,660円）。

- **数量が2以上の行の税額の作り方。**
  行合計に税率を掛けるのではなく「単価×0.1 を四捨五入して数量倍」。
  実機202件で、両者が食い違う **32行はすべて後者**（前者だけが正解になる行は0行）。
  仕様書の実例（単価155×10個 → 税160・税込1710／185×9 → 税171）と一致。
  **総額は変わらない。** 帳票に出る「消費税」は課税額計×10% の一括四捨五入のままでよい
  ことも実機196件で確認した（残り5件は税抜き表示の見積で税額0）。

- **ファイル情報の作成日が更新されていなかった。**
  生成物すべてがテンプレートの作成日（2026/03/11）のままだった。

#### 採用しなかったもの（根拠つき）

- **部品名 → 部品コードの辞書**（`part_code_names.json`、全車種の 12.DB から作った 23,404 語）。
  本番（Streamlit Cloud）には ADDATA が無いので、これがあれば帳票の「ｺｰﾄﾞ」列を埋められる。
  実機202件・10,691行で「品名だけからコードを当てられるか」を測ったところ、
  **最良の条件（占有率95%以上）でも正解率 93.7%**。6% が別の部品コードになる。
  「同じ部品」が絶対条件の協定見積では、誤ったコードが並ぶより空欄が安全なので見送った。
  配布パッケージ側がこの辞書を「その車種の 12.DB にあるコードに絞ってから使う」
  設計にしているのも同じ理由だと分かった。

- **値引きを `Total.pt_ExtraTotal` / `wg_ExtraTotal` に入れる**という指摘は誤りだった。
  実測: 部品100,000 − 値引20,000 → 課税額計80,000・消費税8,000・総額88,000 と正しく反映されている
  （値引きは負の工賃の明細行として入る）。

#### 規則を1か所にまとめた（`neo_rules.py`）

同じ規則を各所に写していたため、**片方だけ直す取り残しが二度続いた**:

- 作業区分の対応表を `app.py` だけ直して `auto_matching` が古いまま（09-10 と 09-11）
- 指数の括弧書きを `app.py` だけ直して `pdf_to_neo_pipeline` が古いまま（09-11）

#### 内包ファイル名が実体より1つ前にずれている

NEO のファイルテーブルは「名前の次に来る size/offset が**次のエントリのもの**」という構造で、

### 5.13　Addata の場所を画面から設定できるようにした（2026-09-11）

#### 何が困っていたか

本番は Streamlit Community Cloud（Linux サーバ）で動いている。
**サーバから利用者のPCの `C:\Addata` は読めない。** パスを打っても届かない。
そのため、これまでは開くたびに ZIP をアップロードし直すしかなく、
アップロードを忘れるとモードA（ベタ打ち）で生成され、部品コードが入らないまま出ていた。

なお **PC 内の Addata は ZIP ではなく普通のフォルダ**（`A`〜`Z` の1文字フォルダ＋`COM`）。
ZIP に固める必要があるのは「サーバに渡すとき」だけで、ローカルで動かすときはフォルダのままでよい。

#### 解決の形

**設定を URL のクエリに残せる**ようにした。一度設定して出てきた URL をブックマークすれば、
**どのPCでその URL を開いても同じ設定で立ち上がる**。
サイドバーの「⚙️ Addata の場所を設定する」から設定する。

| # | 設定 | クエリ | どこで効くか |
|---|---|---|---|
| ① | フォルダのパス | `?addata_dir=` | **アプリが動いているマシンから見える場所だけ**。ローカル起動・社内サーバ・Docker のボリューム |
| ② | 取得URL（ZIP の置き場所） | `?addata_url=` | **クラウドでも効く**。OneDrive / SharePoint / Google ドライブの共有リンク可。実用上はこれ |
| ③ | ZIP アップロード | （残らない） | その場かぎり。従来どおり |

`find_addata_dir()` の解決順序は **アップロード ＞ ①パス ＞ ②URL ＞ 環境変数/secrets ＞ 自動検出**。
この順序は `reg_settings.py` の 6 で `inspect.getsource()` を使って固定してある
（入れ替えると「設定したのに効かない」が起きるため）。

共有リンクはそのまま取りに行くと HTML のプレビュー画面が返ってきて ZIP にならないので、
`normalize_share_url()` でダウンロード用の形に直す
（SharePoint/OneDrive は `download=1` を付与、Google ドライブは `/file/d/<id>` → `uc?export=download&id=<id>`）。

#### 自分で見つけて塞いだ穴（SSRF）

**このアプリの URL は誰でも開ける。** `?addata_url=…` を仕込んだリンクを踏ませれば、
**サーバに任意の宛先を叩かせられる**（踏み台にされる）。
クラウドの内部メタデータ `169.254.169.254` や社内の機器が狙われる。
実装の途中で気づいて次を入れた。

| 塞いだもの | やり方 | テスト |
|---|---|---|
| スキーム | `http` / `https` 以外を弾く（`file://` `ftp://` 等） | 2 |
| 社内・自分自身（IP直書き） | **「インターネットから届くと言い切れないものは全部止める」**。private / loopback / link-local / reserved / multicast / unspecified に加えて `not ip.is_global` | 3・3b3 |
| IPv6 に包んだ内側 | `::ffff:127.0.0.1`（IPv4-mapped）・`2002:7f00:1::`（6to4）・Teredo をほどいて中身で判断。**6to4 は `is_global` が True になるので、ほどかないと通っていた**（実在した穴）。Teredo は `2001::/23` に入っていて `is_private` が True なので元から止まっていた（ほどく処理は二重化） | 3・3f〜3f4 |
| 社内と分かる名前 | `metadata.google.internal` `metadata.goog` `instance-data`、`.internal` `.local` `.localdomain` `.home.arpa` で終わる名前。末尾ドット（`LOCALHOST.`）も正規化 | 3 |

| **リダイレクト経由** | `_GuardedRedirect` で転送先も同じ基準にかける。加えて上の `_safe_connect` は opener に組み込んであるので**転送先の接続にも同じ検査がかかる** | 3b |
| プロキシ | `ProxyHandler({})` で環境変数のプロキシを無効化。プロキシを挟むと実際に繋ぐ相手がプロキシになり、宛先の検査が意味を失う | — |
| 応答の大きさ | `Content-Length` で事前に弾き、読みながらも 300MB で打ち切る | 4g |

| 共有ドライブのリンクが読めない | Google ドライブの共有ドライブは `resourcekey` が無いと中身が返らず、許可を求める HTML が返る（＝ZIPでないとして弾かれ、設定したのに Addata が読めない） | 組み立て直すときに `resourcekey` を持っていく | 1g |
| 取り込みの最中に消される | 印を**展開を始める前**に打つ。展開先は `addata_url_*` なので、展開している最中に別のセッションの回収に消されうる | 7e15 |
| 生成中の展開先を消される | 同じプロセスを複数の利用者が使うので、量による回収が**別のセッションが生成に使っている最中の展開先**を消すと、その場で照合が崩れる。`.inuse/<セッションの札>`（**30分**で失効。印は場所を渡すときに打つが、そのあと OCR・解析・照合で数分かかるため）を置き、**印の無いものを先に**捨てる。印のあるものは、印の無いものを全部捨ててもまだ超えている場合だけ（一時領域が尽きるとアプリごと止まるため）。消えた場合も `cached_root` の妥当性検査が外れて取り直しになるので、**別のデータベースで照合されることはない** | 7e10〜7e14 |
| 目録の大きさ | `zipfile.ZipFile()` は組み立ての時点で目録を丸ごとメモリに載せる。しかも**読み進める条件は本数ではなく目録のバイト数**なので、「本数は小さく、バイト数は巨大」と書けば本数の検査をすり抜けて落とせる。**開く前に**目録の末尾（EOCD／ZIP64）から本数とバイト数の両方を読んで弾く | 4t〜4w3 |
| 中身 | 先頭2バイトが `PK` でなければ ZIP でないとして弾く。**読みながら**見て、違えばその場で打ち切る（Content-Length を付けない相手だと大きさを先に知れないため、最後まで読んでから捨てると上限いっぱい読まされる） | 4e・4l・4m |
| 取り込み済みの使い回し | 使う前に URL を検査する。後回しだと「前に取れているから」で、いま許されない宛先が通ってしまう | 7c |
| 合言葉入りのURL | `https://利用者名:合言葉@example.com/…` を弾く。**この設定はURLに残して共有される**のが前提なので、合言葉が履歴・ブックマーク・共有リンク・ログにそのまま残る。`@` の前を本当の宛先だと読み違えさせる細工にも使われる | 2c・2d・2e |

検証や社内サーバ運用のときだけ環境変数 `ADDATA_ALLOW_INTERNAL_URL=1` で開けられる。
**本番では立てない。**

#### 取得URLが取れなかったとき、別の Addata に落ちてはいけない（Codex 指摘）

はじめは、取得URLが失敗すると環境変数・secrets・自動検出へ順に落ちていた。
これは**この案件でいちばん危ない形**だった。

同じブックマークを別のPCで開いたとき、そのPCに `C:\Addata` が入っていれば、
**取得URLが死んでいても黙ってそちらで照合される**。
版が違えば標準品番も標準指数も変わるのに、画面はいつもどおりで気づけない。
協定見積として保険会社に出すファイルなので、これは通せない。

いまは `find_addata_dir()` が、**取得URLが設定されているのに取れなかった場合は
そこで `None` を返す**。落ちる先があっても使わない。
結果はベタ打ち（モードA）で、金額・明細・品名は見積書のとおりのまま出る。
理由はサイドバーの警告にも出す（設定画面をたたまれていると気づけないため）。

「フォルダのパス」の設定は従来どおり下へ落ちる。パスは元々マシン依存で、
クラウドでは必ず見えない ＝ 取得URLへ進むのが正しい経路だから。

実機で確認した: 許可フラグ無しで `?addata_url=http://127.0.0.1:8532/Addata.zip` を開くと、
**このPCに実在する `C:\Addata` に落ちず**「Addataフォルダ未検出」＋理由が出た。

#### 同じURLを複数の利用者が同時に開いたとき（Codex 指摘）

はじめは「URL ごとに1つの展開先を作り、取り込むたびに `rmtree` してから展開」していた。
本番はクラウドで、**同じブックマークを複数人が開く**。
Aさんが生成している最中に Bさんの取り込みが同じ場所を消すと、
Aさんの Addata が突然消えて**静かにモードAへ落ちる**（エラーにならないので気づけない）。

形を変えて、消す経路そのものを無くした。

| 置くもの | 場所 | 消すか |
|---|---|---|
| 目印 `.addata_root`（JSON: `base` / `root` / `fetched`） | `addata_url_<URLのハッシュ>` | 差し替えのみ（別名で書いて `os.replace` 一発） |
| 中身（展開した Addata） | `addata_url_<ハッシュ>_<毎回違うid>` | **消さない。** 古くなったものは掃除が回収 |

**取り込み直している最中だけは上限を超える。** 「古いぶん＋落とした ZIP＋新しいぶん」が
同時に載るため。先に古いぶんを消すと、**それを使って生成している別のセッションの
足元が崩れる**（部品コードだけ静かに落ちる）ので、この順序は意図的。
落ち着いた状態では、展開のあとの回収で上限に戻る。

古さの判定は**2つを別物として扱う**のが要点。

- 取り直すかどうか → 目印の `fetched`（取り込んだ時刻）
- 掃除が消してよいか → フォルダの更新時刻（最後に使った時刻。`cached_root` がヒット時に更新）

混ぜると「使い続けているだけで永久に取り直さない」か「使用中に消される」のどちらかになる。

#### 画面まわりで踏んだもの

| 症状 | 原因 | 直し |
|---|---|---|
| 見えないパスを入れると**取得URLを1つも保存できない** | パスが見えないことを保存の失敗にしていた。クラウドではパスは必ず見えないので、両方入れる正しい使い方が通らなかった | 注意書き（warning）を出したうえで保存する。探す順番の側では見えないパスは黙って飛ばして取得URLへ進む |
| その注意書きが一瞬も見えない | `st.rerun()` で描き直すと、その前に出した warning は消える | session_state に置いて、描き直したあとに出す |
| 「設定を消す」を押しても欄に前の値が残り、次の保存で書き戻る | Streamlit は `key=` を付けた入力の値を session_state で持っていて、描き直しでは `value=` よりそちらが優先される。**確定したあとに session_state から消そうとすると拒まれる**（例外が `try/except` に握り潰されて、直したつもりで直っていなかった） | 入力欄の名前に番号を付け（`addata_url_input_<n>`）、消すときに番号を進めて**別の入力として作り直す** |
| 時間切れの理由が出せず画面ごと落ちる | 打ち切りを**文字列で見分けていた**。文面は「取得に時間が…」と「名前の解決に時間が…」の2種類あり、後者だと `str.index` が `ValueError` を投げる | 文字列をやめ、包まれた例外の**型**（`URLError.reason` が `TookTooLong` / `BlockedAddress` / `socket.timeout` か）で見分ける |

#### 通しで確認したこと（実機の Addata で）

ローカルに HTTP サーバを立てて実物の Addata から作った ZIP を配り、
`?addata_url=http://127.0.0.1:8532/Addata.zip` で開いて確認した。

- サイドバーの表示が `Temp\addata_url_8fbf2048ec274f06\Addata` になる
  （**自動検出の `C:\Addata` ではない** ＝ 設定が確かに優先されている）
- 車種特定が通る（`KA81` 逆引きで 型式指定 18164 ／ 類別 0010）
- 照合が L2 で当たり、生成物に `ｺｰﾄﾞ='3810'` `品番=52159-B2A20-C0` が入る
- 存在しないパスを入れると「このアプリが動いているマシンからは見えません」で弾かれ、
  **アプリは落ちない**（設定に失敗しても従来どおりモードAで動く）

### 5.14　新旧のコードが混ざったまま動いていた（2026-09-11・本番障害）

#### 症状

本番で PDF→NEO 変換が**丸ごと**失敗した。

```
PDF→NEO変換に失敗しました:
process_pdf_to_neo() got an unexpected keyword argument 'source_mime'
```

#### 原因

**Streamlit はメインスクリプト（`app.py`）を実行のたびに読み直すが、
`import` したモジュールは `sys.modules` に残ったままで、プロセスを
再起動しない限り古い版がメモリに居座る。**

本番は「`app.py` は新しいのに `pdf_to_neo_pipeline` は古い」状態だった。

| 確かめたこと | 結果 |
|---|---|
| 本番画面に当日追加した機能（Addata の場所設定）が出ているか | 出ている → `app.py` は最新 |
| その `app.py` が `source_mime` を渡す形か | 渡す（`c73f628` で追加） |
| 本番で `source_mime` が受け付けられるか | 受け付けない → pipeline は古い |
| 手元で「新 app.py ＋ 旧 pipeline」を作ると | **一字一句同じエラー** |
| Streamlit を起動したままファイルを新しい版に差し替えると | 表示は古いまま変わらない（実測） |

#### なぜ放置できないか

引数が増えた場合は例外で止まるので気づける。**恐いのは中身だけが変わった場合**で、
そのときは何も言わずに古い規則で `.neo` が出る。たとえば `neo_rules` の
作業区分の対応表が古いままだと、区分コードの違う見積が黙って出来上がる。

さらに悪いことに、`pdf_to_neo_pipeline` は
`from app import generate_neo_file` と**生成の本体を `app` から取っている**。
`streamlit run app.py` では画面側は `__main__` として動くので、
`sys.modules['app']` はそれとは**別の二重読み込み**であり、独立に古くなる。
つまり画面は新しいのに、生成の本体だけ古い、ということが起こりうる。

#### 直し方

ファイルの中身そのもの（sha256）でメモリとディスクを突き合わせ、
ずれていれば**依存の浅い順に読み直す**。揃えられないときは、
古いまま走らせずに断る。

| 仕組み | 役目 |
|---|---|
| `_APP_MODULES` | 揃える対象。`neo_rules` → `neo_header` → `addata_locator` → `addata_settings` → `_addata_db_search` → `_grade_identifier` → `addata_vehicle_resolver` → **`app`** → `auto_matching` → `pdf_to_neo_pipeline` |
| `_APP_MODULES_NEVER_RELOAD` | **読み直してはいけない**もの。`_pdfium_lock_mod`（pdfium のロックをプロセスで1つにする。読み直すと別のロックができて共有の意味が消え、Cヒープが壊れてプロセスごと落ちる）と `_process_state`（下記。読み直すと数が 0 に戻る） |
| `_process_state.py` | 「いま変換中か」の数をプロセスで1つ持つ。**`app.py` の変数に置いてはいけない** — Streamlit は `app.py` を rerun のたびに `__main__` として実行し直すので、セッションごとに別物になり、**別のセッションからは「誰も変換していない」ように見えて**足元で差し替わる（Codex 指摘）。数は `max(0, n-1)` で減らす（負に回り込むと以後ずっと誤認する） |
| `sync_app_modules()` | 指紋がずれているものを読み直す。**変換中は見送る**（走っている変換の足元で規則が変わる） |
| `_load_pipeline()` | 揃えてから pipeline を返す。**揃わなければ断る** |
| `_call_pipeline()` | 受けられない引数が1つでもあれば断る。**黙って落とさない**（`is_tax_inclusive` が落ちれば税込の見積が消費税ぶん膨らみ、`expenses` が落ちればレッカー代が1円も入らず、`source_mime` が落ちれば写真を PDF として読もうとする） |
| `_conversion_guard()` | 変換中・Addata 取得中であることを示す。Addata の取得は最大120秒で、その最中に `addata_settings` を読み直されると時間切れの見張り役が持ち場を失う |

`app` を読み直しても画面は走らない。描画は `if __name__ == '__main__':` の中にあり、
`st.set_page_config` も関数の中にあるため（実測で確認済み）。

#### 効きめ（本番と同じ状況を手元に作って実測）

```
① 起動時の pipeline : source_mime を受けるか = False
② 普通に import し直しても                   = False  ← 本番はこの状態
③ 揃える前のずれ    : ['neo_rules', 'neo_header', 'app', 'pdf_to_neo_pipeline']
④ 揃えたあと        : source_mime を受けるか = True （0.02 秒）／残ったずれ: []
⑤ 写真で呼ぶ        : 通った（本番のエラーは出ない）
⑥ 揃えたあとの生成  : 2 行 [('Rrﾊﾞﾝﾊﾟｶﾊﾞｰ', 38600, -1), ('Rﾌﾛｱﾊﾟﾝ', -1, 15070)]
```

**アプリの再起動を待たずに、push だけで直る。**

#### 教訓

- 「本番に反映した ＝ 本番で動いている」ではない。**Streamlit は
  メインスクリプト以外を読み直さない。**
- **プロセスをまたいで共有したい状態を `app.py` に置かない。** Streamlit は
  rerun のたびに `app.py` を実行し直すので、セッションごとに別物になる。
  共有したいものは読み直さない専用モジュールへ（`_pdfium_lock_mod` /
  `_process_state` がその形）。
- 今後モジュールを増やしたら `_APP_MODULES` に足すこと。
  足し忘れると、そのモジュールだけ古いまま黙って動く。
  `tests/reg_pipever.py` の 8 で主要なものは固定してある。
- `process_pdf_to_neo` に渡す引数を増やしたら `_PIPE_ARGS_EXPECTED` にも足すこと
  （テスト 7b/7c がソースから突き合わせている）。

### 5.15　生成の中核で金額が静かにずれていた（2026-09-11）

`.neo` を書く本体を通しで見直して見つけたもの。**5件とも実際に動かして
実在を確認**してから直した。

| # | 症状 | 実測 |
|---|---|---|
| 1 | 税込表記 × 数量2以上で、実機の規則（単価で丸めて数量倍）が効かない | 単価171×10個で税抜が **5円ずれる**（6件中4件で食い違い） |
| 2 | 税込総額が「税抜＋消費税」で表せないとき、**警告なしで1円ずれる** | 100,006円 → **100,007円**。該当は11円に1個（約9%） |
| 3 | 数量100以上で注記が99に丸められる件、**一発生成の経路で警告が出ない** | 警告は1か所だけだった |
| 4 | 管理領域の金額が読めないと、**前案件の金額が残る** | `neo_header.build` は `if totals:` で金額欄に触らない |
| 5 | 生成が落ちると、**顧客情報入りの一時DBが残る** | 実測で1個残った |

#### 1 と 2 は同じ根から来ている

税込表記の見積では、行ごとに税抜を逆算する。そこに2つの間違いがあった。

- **行の逆算**が「行合計から一気に」だった。実機は「単価から逆算して数量倍」。
  税抜表記のときはこの規則が入っていたのに、税込のときだけ抜けていた。
  さらに、合計を合わせるための差額配分（±1円）がその行を書き換えて、
  規則を壊していた。→ **数量2以上の部品行を配分の対象から外した。**
  その行の税抜額は規則で決まっており、1円動かすと規則から外れる。
- **総額**を `税抜 + 四捨五入(税抜×0.1)` で作っていた。この形で表せない
  税込総額が11円ごとに1つある。表せないときは「いちばん近い額」を採って
  進んでいた。→ **税額を「原本の税込 − 逆算した税抜」で書く。**
  部品と工賃は**別々に**差額で確定させる（まとめると部品で出た端数が
  「いちばん金額の大きい欄」に寄せられ、総額は合っていても内訳がずれる）。

#### 「コグニは税抜から計算し直す」は誤りだった（実機で確認）

コードには次のように書かれていた。

> コグニセブンは税抜で保存して消費税を計算するので、実際に .neo に
> 入る総額は必ず S + round(S*0.1) の形になる

この前提が正しければ、総額を原本に合わせても意味がない。根拠の記録が
どこにも無かったので、**実機（コグニセブン）が作った `.neo` 176件を調べた**。

```
税額 = 四捨五入(税抜×0.1) : 166 件
ちょうどでない            :  10 件（約6%）
  税抜 295,455 → 税額 29,545（10%なら 29,546）
  税抜 218,181 → 税額 21,819（10%なら 21,818）
  税抜 545,455 → 税額 54,545（10%なら 54,546）
```

**コグニは書かれた税額をそのまま持っている。** 前提は誤りだった。
`best_intax_for` の説明をこの事実に書き換え、「金額の正解として使っては
いけない」と明記した。画面に出していた
「この税込額は `.neo` では作れないので合計が1円変わります」という断りも、
いまはずれないので消した（残すと誤った案内になる）。

調査に使ったのは `OneDrive\JAA\AcesReport\見積データ` ほか、実案件の
`.neo` 1,537 件から 400 件を無作為抽出したもの（うち176件が読めた）。
**金額の統計だけを取り、顧客情報は読んでいない。**

#### 教訓

- **「実機はこうなっている」と書くときは、根拠も一緒に残す。**
  根拠の無い前提が長く残り、それに合わせてテストの期待値まで
  「1円ずれてよい」に寄っていた（`reg_expense` が `best_intax_for` を
  原本の総額として期待していた）。
- 同じ規則を「税抜のとき」「税込のとき」で別々に書くと、片方だけ古くなる。
  1 はまさにそれだった。

### 5.16　一発生成では事故・保険情報が1つも入っていなかった（2026-09-11）

利用者から「車検証情報が全く反映していません。車検証情報や事故番号等

### 6.1　消費税まわりで実機が本当にやっていること（2026-09-11 実測）

`§5.15` の直しの根拠。**コードに書かれていた前提が誤っていた**ので、
実機のファイルと実機が印刷した見積書で確かめ直した。

#### (1) コグニは `.neo` に書かれた税額をそのまま印刷する（再計算しない）

実機が印刷した見積書 PDF と、対になる `.neo` が3組ある
（`C:\Users\R-T\Desktop\工場見積\0401****.neo` と同名の `.pdf`）。

| ファイル | `.neo` の消費税 | `.neo` の総額 | 紙にその額が出ているか |
|---|---:|---:|---|
| 04011324 | 26,729 | 294,019 | **両方とも出ている** |
| 04011351 | 57,294 | 630,234 | **両方とも出ている** |
| 04011406 | 35,606 | 391,666 | **両方とも出ている** |

コードには「コグニセブンは税抜で保存して消費税を計算するので、`.neo` に
入る総額は必ず `S + round(S*0.1)` になる」と書かれていたが、**誤り**。
書いた税額がそのまま紙に出る。だから税込表記の見積では、
**税額を差額で書いて総額を原本に合わせてよい**（§5.15 の [2]）。

#### (2) 税額の作り方は「課税額計 × 10%」が基本（実機220件）

| 作り方 | 件数 |
|---|---:|
| 四捨五入(課税額計 × 10%) と一致 | 215 / 220（97.7%） |
| 明細行の税額の合計と一致 | 7 / 220（3.2%） |

**請求書単位で1回だけ丸める**のが実機の原則。アプリも同じにしてある。

#### (3) ただし端数がちょうど 0.5 のときは一貫していない

課税額計の下1桁が 5 になる見積 100 件を調べた。

| 実機の挙動 | 件数 |
|---|---:|
| 切り上げ（四捨五入と同じ） | 81 |
| 切り捨て | 19 |

**実機自身が一貫していない。** 19 件の中身をさらに調べたところ、
**13 件は「区分ごとに丸めて足した合計」**だった。

```
  部品計 385,250 → 税 38,525（ちょうど10%）
  工賃計  47,360 → 税  4,736（ちょうど10%）
  諸経費   4,000 → 税    400
  ──────────────────────
  足すと 52,545 = 実機の税額と一致
```

つまり実機には**2つの計算方法が混在している**。

| 作り方 | 実機での多さ |
|---|---|
| 課税額計 × 10% を一括で丸める | 主流（220件中215件） |
| 区分ごとに丸めて足す | 少数（端数.5の19件中13件ほか） |

アプリは `jpy_round`（四捨五入・`ROUND_HALF_UP`）で**主流のほうに統一**している。
少数派と1円違うことはあるが、**アプリの正解は「元の見積書と一致すること」**で
あって実機の内部実装の再現ではない。原本との一致は `reg_pipeline` の
144ケースで担保している。

なお、区分ごとの内訳（部品計の税・工賃計の税・諸経費の税）の合計が
`tx_Total` に一致することは、どちらの作り方でも守られている。
アプリもそこは合わせてある（`_tax_resid` の調整、および税込表記のときは
区分ごとに差額で確定させる — §5.15 の [2]）。

#### (4) 数量2以上の行は「単価で丸めて数量倍」（実機1,203行）

| | 行数 |
|---|---:|
| 単価で丸めて数量倍（実機の規則） | 1,201 |
| そうでない | 2 |

99.8%。`§6` の既存の結論を、さらに大きな標本で裏付けた。
`§5.15` の [1] で、税込表記のときもこの規則が効くようにした。

### テストを書くときの教訓

**テストが実際にバグを捕まえることを確かめてから合格とすること。**
2026-09-10 に、追加した検査を `sys.exit` の後ろに書いてしまい、

このセッションで、以下の穴を実際に踏んだ：

- `reg_cache.py` はハーネスが毎回キャッシュを消しており、
  検証したい経路を素通りしていた
- `reg_expense.py` は `.neo` **内部の**整合しか見ておらず、

いずれも「修正前のコミットを worktree に取り出して、そこで実際に FAIL するか」
を確かめて初めて分かった。新しい回帰テストは必ずこれをやること。

```

XROOT=/tmp/wt_pre python3 reg_xxx.py     # ここで FAIL すること
git worktree remove --force /tmp/wt_pre
```

ADDATA の探索に**壁時計の上限**を入れた（既定20秒・`ADDATA_SCAN_SECONDS`）。
応答しない共有や未同期の OneDrive では `os.listdir` が返らず、

60秒だけ覚えて、そのあと探し直す（永久に未検出でも、毎回フルスキャンでもない）。

スキルとこのアプリで値が違っていた欄を、実機が作った `.neo` 150件・
6,024行で数えて決めた。

| 欄 | 実機 | 直す前のアプリ |
|---|---|---|
| `ERParts.OrderFlag` と AnSMB の [100] バイト | **同じ欄**。120件4,875行で1行も食い違わない。`'0'`（マスタ由来）87.2% ／ `' '`（手入力）9.2% ／ `'9'` 2.3% | ERParts に `'9'`、AnSMB に `'0'`/`' '` ＝ **同じ .neo の中で矛盾** |

### 11.5 今回は変えなかった相違

部品計・工賃計の税額欄（`ms_PartsTotalTax` / `ms_WageTotalTax`）は、
スキルが「行ごとの税の合計」、このアプリが「合計×10%」。
実機295件では **92.5% がどちらとも一致**、行ごとだけ一致 6.1%、
一括だけ一致 1.4% で、行ごとの方が実機に近い。
ただし**総額の税は一括丸めが正**（実機97.9%）で、内訳と総額の整合の
取り方が未解明のため、総額が原本と1円も違わない今の作りを優先して据え置いた。

このアプリに無くてスキルにある機能（塗装パネル別指数・ADAS・板金ランク・
リサイクル部品・レバーレート推定・費用行の任意名など）は、
不具合ではなく機能差。必要になったら移植を検討する。

### 12.9 別の PC で使うときの ADDATA の見つけ方と設定 — 2026-09-14

**結論（別 PC で何をすればよいか）**

- **Windows PC にコグニが入っていて ADDATA が `C:\Addata` か `D:\Addata`** → 何も設定しなくてよい。自動検出する（2026-09-14 に、環境変数も設定ファイルも無い状態を模擬して `C:\Addata`（2026/09 版）を検出することを確認）。サイドバーに「Addata検出済み」とパスと版が出る
- **ADDATA が別の場所**（外付け・共有・OneDrive の中など）→ サイドバー「Addata の場所を設定する」にフォルダのパスを入れる。または pdf-to-neo スキルの `python .claude/skills/pdf-to-neo/scripts/env_check.py --save` を一度実行すると設定ファイルに保存され、アプリもそれを読む（同じ PC で 2 つの実装が別の版を掴まない）
- **ADDATA が複数の版ある PC** → 自動検出は版の新しい方を採る。どれを使っているかはサイドバーの「データ版」で必ず確認する（版が違うと標準品番・標準指数が変わる）
- **本番（Streamlit Community Cloud）から使う** → サーバは利用者の PC の `C:\Addata` を読めない（サイドバーのパスに `C:\Addata` と書いても「このアプリが動いているマシンからは見えません」になる。2026-09-14 に亮平さんが本番で確認）。**サイドバー「🖥️ PC の Addata をこの画面から使う」の「📂 PC の Addata フォルダを選ぶ」で PC の `C:\Addata` を選ぶ**（§12.10）。取得URL（ADDATA を ZIP にしたものの URL。`?addata_url=…`）は代替で、300MB までしか取りに行けないので ADDATA 全体（必要分だけでも 1.9GB）は渡せない。7z は `packages.txt` で入る（§12.8）
- **API キー**: ローカル起動なら `.env` の `GEMINI_API_KEY`（Claude を使うなら `ANTHROPIC_API_KEY`）。Cloud なら Secrets に同じ名前で。両方あれば画面で読む AI を選ぶ。Gemini だけならそれで動く（2026-09-14 に実画面で確認: gemini-3.8-flash、2 ページ、読み直し 1 回、合格、NEO と確認箇所シートをダウンロード可）

- **失敗の見え方**: ADDATA が決まらない → 警告「Addata が決まっていないので、部品コード・標準指数を引く生成はできません」と **「✏️ ベタ打ちで生成」** のボタン（§12.11）。キー無し・無効 → Gemini API のエラー文がそのまま出る。壊れた PDF → 「PDF を開けない」。JPG/PNG は PDF に変換して読む（HEIC は `pillow-heif` が要る）

### 12.10 PC の Addata をブラウザ経由でクラウドのアプリに渡す（橋渡し）— 2026-09-14

**何が問題だったか**: 本番（Community Cloud）はサーバが Linux で、利用者の PC の `C:\Addata`（5.3GB）を読めない。ZIP のアップロードは 200MB、取得URL は 300MB が上限で、必要分（COM 9MB ＋ 各車種フォルダの `*.DB`・`*LTB.CHM` ≈1.9GB）でも渡せない。亮平さんの指示「アプリ側から PC 側にある ADDATA を確認して対応するように改修」への答えがこれ。

**仕組み**（`neo_skill/bridge.py`、`neo_skill/addata_bridge/index.html`、`neo_skill/_runner.py` の `resolve_vehicle`、`app.py` の `p2n_read`/`p2n_make`）:

1. サイドバーの折りたたみ「🖥️ PC の Addata をこの画面から使う」に Streamlit のカスタムコンポーネント（`index.html`。部品ライブラリを使わず postMessage 規約を素の JS で実装）を置く。ボタンでブラウザの **File System Access API**（`showDirectoryPicker`。Chrome / Edge、HTTPS か localhost）で PC の Addata フォルダを選んでもらう
2. 部品は **COM フォルダ（69 ファイル・約 9MB）だけ**を base64 で送る。サーバはセッション専用の一時フォルダ `addata_bridge_<id>` に Addata の形（`COM/`）で置き、`find_addata_dir()` の最優先（順 0）にする。サイドバーに「PC の Addata（フォルダ名）を使用中 ／ データ版 …」と出る
3. 見積を入れて生成すると、アプリは **読む（`p2n_read`）→ 車種を決める（`bridge.resolve_car` → vendor の `AddataVehicleResolver`。COM だけで決まる: W69・J87 で全 ADDATA と同じ confirmed を確認）→ その車種フォルダが無ければ読み取り結果を `session_state['_bridge_pending']` に取り置いて `_bridge_want` に車種コードを入れ rerun** する
4. 部品は render の引数 `want` を見て、その車種フォルダ `<A-Z>/<車種>/`（`*IMG.CAB` は送らない。数 MB）を送る。届いたら `_bridge_want` を消し、STEP 1-A の先頭で取り置きから **作る（`p2n_make`）**。車種が決まらなければそのまま作る（汎用車種の経路）。PC に車種フォルダが無ければ部品が `error` を返し「車種 … のフォルダを PC の Addata から取り込めませんでした」で不合格

### 12.12 添付した車検証・事故/保険の書類を NEO に反映する — 2026-09-14

亮平さんの指摘「ベタ打ちで顧客名・車検証情報・保険会社情報が NEO に入らない」→ 原因は 2 つ。①ベタ打ち（旧経路）に STEP 1-B の車検証を渡していなかった（旧経路は見積書そのものを車検証として OCR して空になり、非マージなので顧客・車両欄を空で上書き）。②保険情報はサイドバーに手で入れる欄しか無く、書類から読む手段が無かった。「添付した写真や車検証から車両情報や保険情報を NEO に反映してほしい」に応えて次を追加:

### 12.13 本番の実機テストとバグハント（Chrome 実操作 → codex 3 本 → 修正）— 2026-09-15

### 12.30 画面（UI/UX）の作り直しと、実画面のバグハント — 2026-09-20

使う人は損害調査員で、毎日この 1 画面しか触らない。「長い 1 枚のフォーム」だった画面を
**上から順に 3 手で終わる流れ**に組み替え、実際にブラウザ（Playwright）で操作しながら直した。

画面の並び（いまの姿）:

1. 濃紺の帯（アプリ名・版・Gemini API の接続・使うモデル）
2. 進み具合の 3 段「見積書を入れる → 「生成」を押す → NEO を受け取る」。**実際の状態から出す**
   （見積書が無ければ段 1、いまの入力から渡せるものができていれば段 3）
3. 案内カード 1 行（できあがっていれば緑の「✅ NEO ができました — 下の 2 つを組で受け取ってください」に差し替え）
4. たたみ「このアプリが何をするか（詳しく）」「金額表記の設定」
5. 見積書のドロップ欄（主役）
6. たたみ「任意の書類を添える（車検証・事故/保険の書類）」。添付があると開いた状態＋見出しに名前
7. 大きな青いボタン「🚀 見積書からNEOを生成」。**見積書が無いときも出す**（押せない状態＋「入れると押せます」）
8. 結果: 合格の帯 → 濃紺のまとめ（車両／合計（税込）／明細の行数／レバーレート）→ 読み取りの注意（2 件以上はたたむ）
   → ダウンロード 2 つ → 「必ず組で渡してください」→ 報告文（たたみ）
9. 下に たたみ「テンプレートNEO（任意）」「PDF でうまく読み取れないとき（CSV で取り込む）」

実画面で見つけて直した不具合:

| 症状 | 原因 | 直し方 |
|---|---|---|
| expander の矢印などが `keyboard_arrow_down` の**文字のまま**出る | 日本語フォント指定が Material Symbols まで上書きしていた | アイコンのフォントを後から効く形で指定し直す |

| 入れたファイルを**外せない**（✕ が消えている） | 小さな文字の一括非表示（`small`）が ✕ のラベルまで巻き込んでいた | 非表示の指定を `:not(...)` で絞る |
| 進み具合が常に①／失敗した結果でも「完了」に見える | 段を固定値で出していた | `_bar_key`・`_bar_fresh` から `_p2n_give_now` を出し、帯とカードで共有（app.py §「進み具合」） |

| 生成ボタンがファイルを入れるまで**現れない** | ファイルがあるときだけ描いていた | いつも描き、無いときは押せない状態＋ヒント |

| **PC が暗いテーマだと、見積書のドロップ欄の文字が消える**（サイドバーのメニューも見えない） | 画面の色は明るい下地に合わせて決めてあるのに、Streamlit 既定の文字色（ほぼ白）が暗いテーマで効く | `.streamlit/config.toml` に `[theme] base = "light"` を足して**明るい方に固定**した |
| 「_要確認」の NEO を渡すときだけ、帯は「NEO を受け取る」なのに上の案内は「入れて押すだけ」 | カードが `ok` のときしか切り替わらなかった | カードを 3 通りにした（要確認＝琥珀／合格＝緑／まだ＝青） |
